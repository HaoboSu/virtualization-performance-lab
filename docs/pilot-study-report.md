# Pilot Study Report: Neighboring-VM CPU Interference in a Virtualized Environment

**Author:** Haobo Su  
**Project:** `virtualization-performance-lab`  
**Study status:** Pilot study  
**Platform:** VMware Workstation on Windows 10 Enterprise

---

## Abstract

This pilot study investigates how CPU pressure generated by a neighboring virtual machine affects the performance of a benchmark workload running in another virtual machine. The experiment uses two Ubuntu Server virtual machines hosted on VMware Workstation. A single-vCPU benchmark VM runs a CPU-bound Sysbench workload, while a two-vCPU contention VM generates synthetic CPU load using `stress-ng`.

Three conditions were evaluated: an idle neighboring VM (baseline), 50% configured CPU load, and 100% configured CPU load. Each condition was repeated five times using a 30-second single-threaded Sysbench CPU test. The pilot produced a clear performance gradient. Mean throughput decreased from 2615.81 events/s at baseline to 2480.66 events/s at 50% configured load and 2252.28 events/s at 100% configured load. Relative to baseline, throughput decreased by 5.17% and 13.90%, respectively. Mean latency increased by 5.24% and 15.18%, while P95 latency increased more strongly, by 19.43% and 36.44%.

The results suggest that, in this experimental setup, increasing neighboring-VM CPU load is associated with lower benchmark throughput and higher latency, with tail latency showing a larger relative increase than mean latency. Because this is a small-scale pilot conducted on a laptop-class host without precise guest-vCPU pinning or direct host-level CPU telemetry, the findings should be interpreted as preliminary. The next stage will expand the configured load levels, increase repetitions, rotate experiment order, and add system-level metrics and a scientific computing workload.

---

## 1. Research Question

The central research question is:

> **How does CPU pressure generated by a neighboring virtual machine affect throughput and latency in a benchmark virtual machine?**

The experiment is designed as a simplified noisy-neighbor scenario. One virtual machine acts as the workload being measured, while the second virtual machine acts as a controlled source of CPU pressure.

The study does **not** attempt to measure virtualization overhead by comparing bare-metal and virtualized execution. Instead, it focuses on **performance interference between co-located virtual machines sharing the same physical host**.

---

## 2. Motivation

Virtualized environments improve hardware utilization by allowing several workloads to share one physical system. However, virtual machines that appear isolated at the software level still depend on shared physical resources such as CPU cores, caches, memory bandwidth, storage, and network interfaces.

When one workload becomes resource-intensive, it may indirectly degrade the performance of another co-located workload. This effect is commonly discussed as a noisy-neighbor or performance-interference problem.

This topic is relevant to:

- cloud computing;
- virtualized HPC environments;
- multi-tenant systems;
- performance isolation;
- resource-aware scheduling;
- workload placement;
- performance engineering;
- HPC–cloud convergence.

The purpose of this pilot is not to reproduce a production cloud platform. Instead, it establishes a small, controlled, reproducible environment in which interference can be generated, measured, analyzed, and progressively refined.

## 4. Experimental Design

The system can be represented as:

```text
Windows 10 Enterprise Host
Intel Core i3-1005G1
2 physical cores / 4 logical processors
8 GB RAM
VMware Workstation
        |
        +--------------------------+
        |                          |
 benchmark-vm                contention-vm
  1 vCPU / 2 GB               2 vCPU / 2 GB
        |                          |
    sysbench                    stress-ng
        |                          |
        +------------+-------------+
                     |
             Observed interference
```

The key design principle is role separation:

- `benchmark-vm` is the measured workload.
- `contention-vm` is the interference generator.

This is preferable to running both Sysbench and `stress-ng` inside the same guest because the goal is to study interference between virtual machines rather than competition between two processes inside one operating system.

---

## 5. Independent and Dependent Variables

### 5.1 Independent variable

The independent variable is:

> **Configured CPU load generated by `stress-ng` inside the neighboring VM.**

The pilot evaluates three levels:

- 0%: contention VM powered on but idle;
- 50%: two `stress-ng` CPU workers configured for 50% load;
- 100%: two `stress-ng` CPU workers configured for 100% load.

The commands were:

```bash
stress-ng --cpu 2 --cpu-load 50 --timeout 240s
```

and:

```bash
stress-ng --cpu 2 --cpu-load 100 --timeout 240s
```

A critical interpretation point is that `--cpu-load 50` and `--cpu-load 100` describe the **configured workload inside the guest VM**. They do not mean that total Windows host CPU utilization was exactly 50% or 100%, and they do not quantify the exact fraction of physical CPU time taken away from the benchmark VM.

For that reason, figures and discussion should refer to **neighboring-VM configured CPU load**, not exact host CPU contention.

---

### 5.2 Dependent variables

The primary dependent variables are:

1. **Throughput**  
   Measured as Sysbench events per second.

2. **Average latency**  
   Mean event latency reported by Sysbench.

3. **P95 latency**  
   The 95th-percentile event latency reported by Sysbench.

Throughput captures how much CPU work can be completed per unit time, whereas latency describes how long events take to complete. P95 latency provides an initial view of the upper tail of the latency distribution and is therefore useful for examining performance variability beyond the mean.

---

## 6. Benchmark Procedure

The benchmark VM runs:

```bash
sysbench cpu --threads=1 --time=30 run
```

Each run lasts 30 seconds and uses one benchmark thread.

For each condition:

- five Sysbench repetitions were collected;
- raw Sysbench output was preserved as separate `.txt` files;
- a short pause was used between repeated benchmark runs;
- the benchmark configuration was kept constant;
- only the neighboring VM workload condition was changed.

The current pilot therefore contains:

```text
3 conditions × 5 repetitions = 15 benchmark runs
```

The raw results are stored under:

```text
results/raw/pilot_v2/
```

---

## 7. Why the Baseline Keeps the Second VM Powered On

In the baseline condition, `contention-vm` remains powered on but does not run the stress workload.

This is an important control decision.

If the baseline used only one powered-on VM while the interference conditions used two powered-on VMs, the experiment would change two factors simultaneously:

1. the presence of the second VM;
2. the CPU workload generated by the second VM.

Keeping the contention VM present in all conditions reduces this ambiguity. The main experimental change is therefore the CPU workload generated inside the neighboring VM.

## 8. Methodological Development

The current pilot configuration was reached after earlier experiments exposed weaknesses in the initial design.

### 8.1 Initial unconstrained pilot

An earlier experiment used one vCPU for each VM. The results suggested measurable interference, but the intermediate contention condition showed more variability than desired.

This raised the question of whether host scheduling behavior was introducing uncontrolled noise.

---

### 8.2 Attempted Windows process-level affinity

To create stronger CPU overlap, both VMware `vmware-vmx.exe` processes were experimentally restricted to the same Windows logical processor using Task Manager CPU affinity.

This approach appeared attractive because it seemed to force the two VMs to share a logical CPU.

However, the resulting baseline became highly unstable. Throughput variability increased dramatically, with an approximate coefficient of variation of 24.6%.

The configuration was rejected.

The methodological lesson was important:

> Windows process-level affinity constrains the entire VMware VMX process, not only the guest-vCPU execution thread.

A VMware VMX process contains more than the conceptual guest CPU execution path. Restricting the whole process can therefore introduce additional scheduling and virtualization bottlenecks that are different from the intended experimental variable.

The project consequently abandoned this affinity method rather than interpreting unstable data as meaningful contention results.

---

### 8.3 Revised pilot configuration

The accepted pilot restored VMware Workstation to normal Windows scheduling behavior.

The final configuration used:

- benchmark VM: 1 vCPU;
- contention VM: 2 vCPUs;
- no manual Windows process affinity.

This configuration produced substantially more stable repeated measurements and became the basis of `pilot_v2`.

---

## 9. Data Processing and Reproducibility

Raw data are preserved without manual modification.

The analysis script is located at:

```text
analysis/analyze_results.py
```

It automatically:

1. scans raw Sysbench result files;
2. identifies the configured load condition from filenames;
3. extracts:
   - events per second;
   - total runtime;
   - total events;
   - minimum latency;
   - average latency;
   - maximum latency;
   - P95 latency;
4. groups repeated runs by condition;
5. calculates:
   - mean;
   - median;
   - sample standard deviation;
   - coefficient of variation;
   - relative degradation or increase compared with baseline;
6. generates processed CSV files;
7. generates performance figures.

Processed data are stored as:

```text
results/processed/pilot_v2_results.csv
results/processed/pilot_v2_summary.csv
```

This structure separates raw experimental output from derived results and makes the analysis reproducible.

## 11. Throughput Analysis

Mean throughput decreased as the configured CPU load in the neighboring VM increased:

```text
0%      2615.81 events/s
50%     2480.66 events/s
100%    2252.28 events/s
```

Relative to baseline:

- the 50% condition reduced throughput by **5.17%**;
- the 100% condition reduced throughput by **13.90%**.

This produces a clear descending pattern across the three pilot conditions.

![Throughput vs neighboring-VM CPU load](../figures/throughput_vs_pressure.png)

The result is consistent with the interpretation that increasing CPU demand in the neighboring VM can reduce the amount of CPU work completed by the benchmark VM in this host environment.

However, the pilot does not directly measure physical CPU allocation, so it should not be interpreted as proving that a known percentage of host CPU capacity was removed from the benchmark VM.

---

## 12. Average-Latency Analysis

Mean latency increased as neighboring-VM load increased:

```text
0%      0.382 ms
50%     0.402 ms
100%    0.440 ms
```

Relative to baseline:

- the 50% condition increased mean latency by **5.24%**;
- the 100% condition increased mean latency by **15.18%**.

![Average latency vs neighboring-VM CPU load](../figures/avg_latency_vs_pressure.png)

The throughput and average-latency results are internally consistent: as the benchmark VM completes fewer events per second, the average time per event increases.

---

## 13. P95-Latency Analysis

P95 latency showed a larger relative change than average latency:

```text
0%      0.494 ms
50%     0.590 ms
100%    0.674 ms
```

Relative to baseline:

- the 50% condition increased P95 latency by **19.43%**;
- the 100% condition increased P95 latency by **36.44%**.

![P95 latency vs neighboring-VM CPU load](../figures/p95_latency_vs_pressure.png)

At the 100% configured load condition, mean latency increased by approximately 15.2%, whereas P95 latency increased by approximately 36.4%.

This is the most interesting observation in the current pilot.

It suggests that neighboring-VM CPU pressure may affect the upper tail of event latency more strongly than the mean in this setup. In other words, interference may affect **performance predictability** as well as average performance.

This interpretation remains preliminary. The current sample size is small, Sysbench latency output has limited decimal precision, and no formal statistical hypothesis test has yet been applied.

---

## 14. Interpretation

The pilot supports three cautious observations.

### Observation 1: Performance degradation follows increasing configured load

Across the three tested conditions, benchmark throughput decreased progressively as the configured `stress-ng` load increased.

The corresponding latency metrics increased.

This indicates that the revised experiment is sensitive enough to detect a workload-interference pattern.

---

### Observation 2: Repeated throughput measurements are relatively stable

Throughput CV values remained below 2% in all three accepted pilot conditions.

This is substantially more stable than the rejected process-affinity experiment and provides evidence that the revised configuration is suitable for further study.

---

### Observation 3: Tail latency may be more sensitive than mean latency

P95 latency increased substantially faster than average latency.

The current data do not establish a general rule, but the pattern provides a clear motivation for a more detailed latency experiment.

A custom benchmark capable of recording individual operation latencies at finer resolution would make it possible to calculate P50, P95, P99, and full latency distributions.

---

## 15. What the Pilot Does and Does Not Show

### The pilot supports the following statements

- Higher configured CPU load in the neighboring VM was associated with lower benchmark throughput.
- Mean and P95 latency increased across the tested conditions.
- P95 latency showed a larger relative increase than mean latency.
- Five-run throughput measurements were relatively stable in the revised configuration.
- The revised configuration is suitable for a larger follow-up experiment.

### The pilot does not establish the following claims

- It does not measure virtualization overhead relative to bare metal.
- It does not prove exact physical-core sharing between the two VMs.
- It does not show that host CPU utilization was exactly 50% or 100%.
- It does not prove that CPU contention alone caused every observed difference.
- It does not establish that the observed P95 behavior generalizes to other workloads, hypervisors, processors, or cloud systems.
- It does not yet provide production-scale evidence.

Maintaining this distinction is important because the purpose of the pilot is to validate the research design and identify a reproducible performance pattern before conducting a larger experiment.

## 16. Limitations

### 16.1 Small sample size

Each condition contains only five repetitions.

This is sufficient for an exploratory pilot but not for strong statistical claims.

---

### 16.2 Only three load levels

The current experiment contains:

```text
0% → 50% → 100%
```

Three points show a clear gradient, but they provide limited information about the shape of the relationship.

The next pilot extension should add 25% and 75% configured load.

---

### 16.3 Laptop-class processor

The Intel i3-1005G1 is a mobile processor with two physical cores and four logical processors.

Its behavior may be influenced by:

- dynamic frequency scaling;
- Turbo Boost;
- thermal limits;
- sustained power limits.

These factors may change benchmark performance over time.

---

### 16.4 Windows host and VMware Workstation

The experiment uses VMware Workstation on Windows 10 rather than a server-oriented virtualization environment such as KVM or Proxmox.

The pilot therefore represents a controlled personal test platform, not a production cloud environment.

---

### 16.5 No precise guest-vCPU pinning

The accepted pilot does not use precise physical-core pinning.

The earlier Windows process-affinity attempt was rejected because it destabilized the baseline and did not provide a clean guest-vCPU placement mechanism.

Actual scheduling remains under Windows and VMware control.

---

### 16.6 Configured guest load is not host utilization

The experimental independent variable is `stress-ng --cpu-load` inside VM2.

No direct host-level CPU utilization measurements were collected during this pilot.

Therefore, the experiment cannot translate the configured guest load directly into a known percentage of host CPU contention.

---

### 16.7 Sequential condition order

The pilot conditions were collected sequentially.

This creates a potential confounding factor because experiment order may correlate with:

- CPU temperature;
- CPU frequency;
- host background activity;
- sustained power behavior.

Future experiments should rotate or randomize condition order.

---

### 16.8 Limited Sysbench latency resolution

The current Sysbench output provides latency values with relatively limited decimal precision.

This is sufficient for a first pilot but limits detailed tail-latency analysis.

---

### 16.9 Single workload

The current experiment uses only the Sysbench CPU workload.

A scientific workload should be added before making broader claims about HPC performance interference.

---

## 17. Planned Next Stage

The pilot establishes enough stability to justify a larger study.

### 17.1 Add intermediate contention levels

Expand the configured load levels to:

```text
0% → 25% → 50% → 75% → 100%
```

This will provide a more informative interference curve.

---

### 17.2 Increase repetitions

Increase from five repetitions to approximately 10–20 repetitions per condition.

This will support more robust estimates of variability and make statistical comparison more meaningful.

---

### 17.3 Rotate or randomize condition order

Instead of always running:

```text
0 → 25 → 50 → 75 → 100
```

future experiments should use rotated or randomized blocks.

For example:

```text
Block 1: 0 → 25 → 50 → 75 → 100
Block 2: 75 → 25 → 100 → 0 → 50
Block 3: 50 → 100 → 25 → 75 → 0
```

This reduces the risk that time-dependent effects are systematically associated with a specific contention condition.

---

### 17.4 Add host and guest metrics

A follow-up experiment should collect additional performance indicators, potentially including:

- host CPU utilization;
- CPU frequency;
- guest CPU utilization;
- context switches;
- CPU migrations;
- run-queue behavior;
- hardware performance counters where available.

The objective is to move from observing a performance effect toward explaining the mechanism behind it.

---

### 17.5 Add a custom latency benchmark

A small C benchmark could record high-resolution timing for individual operations.

This would allow calculation of:

- P50 latency;
- P95 latency;
- P99 latency;
- full latency distributions.

This is particularly relevant because P95 latency showed the strongest relative increase in the current pilot.

---

### 17.6 Add a scientific HPC workload

A key extension is to reuse a numerical workload derived from the author's previous HPC work, such as a 3D Laplace / Gauss–Seidel solver.

This would allow the project to compare:

1. a synthetic CPU microbenchmark;
2. a scientific computing workload.

A stronger research question would then become:

> **Does neighboring-VM CPU pressure affect a synthetic CPU benchmark and a numerical HPC workload in the same way?**

This would connect virtualization performance analysis directly with HPC workload behavior.

---

### 17.7 Reproduce on a second virtualization platform

If resources permit, the experiment could later be reproduced on a Linux host using KVM or Proxmox.

A second platform would help distinguish findings that are specific to the current Windows/VMware environment from more general virtualization-interference effects.

## 20. Conclusion

This pilot study developed and validated a small reproducible framework for examining neighboring-VM CPU interference.

The accepted pilot produced a consistent three-level performance pattern:

- throughput decreased as configured neighboring-VM CPU load increased;
- mean latency increased;
- P95 latency increased more strongly than mean latency;
- repeated throughput measurements remained relatively stable.

The strongest observed condition, 100% configured neighboring-VM CPU load, reduced mean benchmark throughput by approximately 13.9% relative to baseline and increased P95 latency by approximately 36.4%.

These results are not treated as general causal evidence. Instead, they demonstrate that the current experimental setup is capable of producing a measurable and repeatable interference signal.

The next stage will expand load levels, increase repetitions, improve experiment ordering, add system-level measurements, and introduce a scientific HPC workload. The broader goal is to move from simple interference detection toward a deeper understanding of performance isolation and workload predictability in virtualized computing environments.
